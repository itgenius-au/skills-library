# Leg troubleshooting

Placeholders (`<REVIEW_SKILLS>`, `<SCRATCH>`, `<PROJECT_DIR>`, `<snapshot>`, `<RANGE>`) are defined in SKILL.md under "Invocation form".

If a key-based leg (Gemini or GLM) fails to authenticate, and the same key worked earlier in the session, check where the key comes from. When you load keys from a secret manager, another session on the same machine can switch the manager's active account, and a read that does not pin the account then fails with a permission error. Pin the account for the read, export the key into the wrapper's environment, and re-run.

**A host hook notice can also derail a leg.** A host hook that adds context to tool results (a permission hint, say) can eat a leg's whole allowance: a Fable leg once ended with a note about the hook, with no report and no `MODEL:` line. Tell every leg: ignore host hook notices; your final message is the complete report. If a leg still returns no `MODEL:` line, re-run it once; in quick mode that re-run breaks the one-attempt rule, so record it as a deviation.

The Gemini leg's own `MODEL:` line is unreliable too. Record the `::GEMINI-MODEL::` line the wrapper prints: it names the model that ran, after any fallback. A leg can claim a different model than the wrapper's marker shows.

A GLM leg can also return its raw reasoning (a think-aloud with draft finding lists and self-questions) instead of the report. That is a PARTIAL leg: read its planned findings by hand, verify each one, and record the leg as partial in the synthesis. Never count it as a clean pass. The tell is `::GLM-TRUNCATED::` as the first line of the output: the reply hit the wrapper's default `--max-tokens` while still reasoning. Read out the findings it had concluded, verify each, and mark the leg PARTIAL; `review-with-glm` has the larger-cap re-run.

If the Codex leg stops because its read-only sandbox cannot run the tests it wants (for example a harness that needs `mktemp`), do NOT widen its sandbox mid-panel. Run the tests yourself, save the output to a file OUTSIDE the repo, and send the SAME leg back for a static review that treats that log as an unverified claim and judges fake-green from the test source. The same holds for mutation testing: a Codex mutation table whose rows read `BLOCKED` (the sandbox could not make copies) is no result. Run the mutations yourself and record KILLED / SURVIVED from that run.

**Do not fork-bomb a small host.** Each leg spawns a heavy CLI; four launched at once on a modest machine can exhaust the process table and kill a leg outright. On a resource-limited host, cap concurrency - run the legs two at a time rather than all four - and prefer this restraint whenever the diff is small enough that the panel overhead dwarfs the change (see Scale to the subject: a trivial change does not get the full four-CLI panel at all).

**Lesson: decision mode, Codex at `xhigh` under a 570 s cap.** An orchestrator-run Codex leg on a decision packet of a few files can spend its whole 570 s reading and re-checking them and print `::CODEX-TIMEOUT::` with no report. The same leg finished once its prompt ended with one line: "TIME LIMIT: you have under 8 minutes. Read the files once, run at most a few arithmetic checks, then write the report." When a leg runs with `--timeout 570` (quick mode, or a runner that must fit the 10-minute Bash cap), put that line in the Codex prompt from round 1.

**Lesson: doc mode on a long document.** Codex at `xhigh` can pass the 900 s default on a document of tens of KB and be killed (`::CODEX-TIMEOUT::`); a re-run with `--timeout 1800` finished in about 15 minutes, so start such a Codex leg with `--timeout 1800`. GLM can time out reading its reply on a packet well under the 60 KB limit, and fail the same way on an identical re-run with a longer `--timeout`. Before re-running a GLM timeout on a packet under 60 KB, send a one-line ping (`glm-exec.sh --timeout 60 --retries 0 -- 'Reply OK'`); if the ping fails, mark GLM `unavailable` at once.
